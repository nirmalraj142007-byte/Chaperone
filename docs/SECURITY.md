# Security

This document is a scored submission artifact in the sense CLAUDE.md means for `friction-log.md`: written from real findings during a real audit pass (Phase 17), not backfilled to look complete. Where a number came in worse than hoped, it's reported as-is.

## Threat model

Chaperone deliberately ingests attacker-controlled text: third-party MCP tool descriptions, refetched from an upstream server on every connect. That text is rendered to a resident in a consent card whose entire purpose is to be trusted, and it is stored verbatim as ledger evidence. Two properties follow directly from that:

- **Escape at render, never at ingest.** `packages/policy/src/canonical.ts` and `diff.ts` never mutate upstream text — it is hashed and stored byte-for-byte, because a hash computed over sanitized text would not be a hash of what the upstream actually sent. Every renderer (`packages/mcp-app/src/render.ts`'s consent card, `packages/console/src/screens/QueueDetail.tsx`'s diff view) sanitizes and escapes its own copy at the point of rendering instead.
- **A resident's approval binds to a hash, never to a rendering.** The security property (`allow()` in `packages/policy`) is a hash comparison, independent of anything a renderer does. A rendering bug is a UI bug, not a bypass — see `packages/policy/test`'s 100%-coverage gate.

## Untrusted-text rendering

Both renderers neutralize the same class of invisible/reordering Unicode control characters — RTL/LTR overrides and isolates (U+200E/U+200F, U+202A–U+202E, U+2066–U+2069) and zero-width characters (U+200B, U+200C, U+200D, U+2060, U+FEFF) — by substituting a same-width space, which preserves `DiffSpan` offsets computed against the untainted original. Both cap a rendered description at 4,000 characters with an explicit truncation marker; the consent card links to `/queue/{quarantineId}` for the full text, the console offers an in-page "show full text" expansion (it's already the full-text destination). Tests: `packages/mcp-app/test/render.test.ts`'s "XSS and hostile-input containment" and "description truncation" suites; `packages/console/test/verbatim.test.tsx` and the `sanitizeInvisibleChars`/`truncateForDisplay`/`clipSpansToLength` cases in `packages/console/test/lib.test.ts`.

## Approval tokens

- Minted with `node:crypto.randomBytes(32)`, base64url-encoded (256 bits of entropy). Only `sha256(token)` is ever persisted (`packages/ledger/src/repos/quarantine.ts`'s `approvalTokenHash`); the plaintext lives in a process-local `Map` for as long as the quarantine stays open and nowhere else — a gateway restart loses it, by design.
- Compared with `node:crypto.timingSafeEqual` after a length check (`packages/gateway/src/approve.ts`'s `constantTimeHexEqual`), never `===`.
- Bound to one `quarantineId` by construction: each quarantine mints its own token/hash pair, and `approveChange` only ever compares against the row keyed by the `quarantineId` the caller supplied. `packages/gateway/test/approve.test.ts` asserts a token minted for quarantine A is rejected against quarantine B explicitly, not just implicitly.
- 24-hour expiry against `detectedAt`, checked in `approve.ts` and re-checked identically (same exported constant, not a second literal) by the consent card's "expired" rendering state.
- **Single-use is enforced by `ledger.resolveQuarantine`'s DynamoDB `ConditionExpression` (`#status = :pending`), called before any side-effecting write.** This was a real bug this phase fixed, not a pre-existing property: `approveChange` previously read `quarantine.status` in application code, then wrote the pin and ledger events, and called `resolveQuarantine` *last* with no condition — two concurrent requests could both observe "pending" before either wrote, and both redeem the same token. `packages/ledger/test/quarantine.test.ts` and `packages/gateway/test/approve.test.ts` both test the fix directly (the latter simulates the race by making the mocked `resolveQuarantine` reject the second racer even though both callers' `getQuarantine` reads returned "pending").
- The plaintext token appears in exactly one place: the `GateDecision`/`ConsentCardModel` returned to whoever tripped the mismatch or is polling `chaperone/pending_changes`. It is never logged — every gateway log call that touches a quarantine logs 12-char hash prefixes only (`shortHash()` in `gate.ts`) — and `ApproveResult` (the response to a redemption) never carries it at all, asserted in `approve.test.ts`.

## Secrets

- `packages/logger/src/index.ts`'s `redactSensitive()` matches keys against `/token|secret|key|authorization/i` and replaces the value with `"[redacted]"`, recursively, through pino's `formatters.log` hook — so it runs on every log line, including ones the request-context mixin contributes to. `packages/logger/test/context.test.ts` asserts `approvalToken`, `GITHUB_TOKEN`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, and `AWS_SESSION_TOKEN` are all redacted together in one real serialized pino line, with a non-sensitive control field surviving alongside them.
  - This is key-name matching, not value-pattern matching: a secret interpolated into a plain message string (`log.info(\`token is ${t}\`)`) rather than passed as a structured field would not be caught. No code path in this repo does that today, but it's a real limitation of the mechanism, not a closed gap.
- `.env` is gitignored (`.env`, `.env.*`, `!.env.example`); `.env.example` is committed and carries only placeholder values.
- **Finding, this phase:** a local, untracked `.env` on the audit machine contained what has the shape of a real GitHub personal access token. `git log --all -- .env` confirms it was never committed — this is a live-machine hygiene finding, not a repo leak. Recommendation: rotate it as a precaution, and prefer a fine-grained PAT scoped to public-repo read only for anything `pnpm crawl:commit-recency` or similar scripts need.
- CI runs `gitleaks/gitleaks-action@v2` against full git history on every push/PR (`.github/workflows/ci.yml`, job `security`). `.gitleaks.toml` extends gitleaks' default ruleset and allowlists `data/raw/crawl-1/**` (committed, timestamped, frozen third-party crawl evidence per CLAUDE.md's calendar gates — real README/metadata text from other people's servers, not this project's secrets) and `packages/crawler/.cache/**` (already gitignored, but still real content on disk for the filesystem-mode scan a developer runs locally).
  - **Not run in this session:** `gitleaks detect --no-git -v` requires the `gitleaks` binary, which isn't installed in this environment, and downloading and executing a new binary automatically is outside what this session does unattended. Run it yourself per the VERIFY block — it will (correctly) flag the local `.env` above if it's still present when you run it; that's the finding, not a false positive.

## IAM

`infra/iam-advisory.json` is a **policy document**, not a deployed role — deployment (Phase 18) hasn't started, so there is no AWS account to audit yet. It defines two roles: `chaperone-gateway-task-role` (the ECS Fargate task role; its `ledger-event` statement grants `PutItem` and reads only, never `UpdateItem`/`DeleteItem`/`BatchWriteItem`) and `chaperone-bedrock-advisory-role` (scoped to `bedrock:InvokeModel`/`Converse` plus read-only `quarantine` access for diff context — no statement names `ledger-event` or `pin` at all). `packages/ledger/test/iam-advisory.test.ts` parses the document and asserts both properties, plus that every table name in it is real and current against `packages/ledger/src/tables.ts`.

Honest gap: `packages/advisory/src/localRunner.ts` does not yet run as an isolated worker under the narrower role — today it executes under the gateway's own role. The bedrock-advisory role describes the deployment target, not current runtime reality; splitting the two is deployment work, tracked separately.

## HTTP surface

- **Headers** (`packages/gateway/src/security.ts`'s `securityHeadersMiddleware`, every response): `Content-Security-Policy: default-src 'none'; base-uri 'none'; frame-ancestors 'none'` (this server only ever emits JSON and SSE, never HTML — a maximally strict CSP costs nothing), `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, and `Strict-Transport-Security` only when `CHAPERONE_ENV=production` (sending it on a plain-HTTP local/demo deployment would be actively wrong, not just unnecessary).
- **CORS** (`apiCorsMiddleware`, `/api/*` only): reflects an origin already on `GATEWAY_ORIGIN_ALLOWLIST`, never `*`, with `Vary: Origin`, and answers `OPTIONS` preflights directly. `/mcp` keeps its existing reject-only allowlist (`originAllowlistMiddleware`) — it isn't meant to be read cross-origin from a browser.
- **Rate limiting** (`packages/gateway/src/rateLimit.ts`): a hand-rolled per-key token bucket, `/mcp` keyed by session id (falling back to client IP pre-session, i.e. on `initialize`), `/api/*` keyed by client IP. Both return `429` with `Retry-After`. `app.set("trust proxy", 1)` trusts exactly the one ALB hop the deployed topology has (CLAUDE.md: ECS Fargate + ALB), so per-IP limiting doesn't collapse every real client behind the ALB into one bucket, without trusting a forgeable `X-Forwarded-For` from further out.
  - The bucket sizes (`MCP_RATE_LIMIT`, `API_RATE_LIMIT` in `rateLimit.ts`) are deliberately generous starting points, not derived from measured production traffic — there isn't any yet. Revisit if a real deployment's traffic pattern turns out to need tighter or looser budgets.

## Crawler isolation

Re-verified, not re-built — Phase 5's design already holds: `--read-only`, `--memory=512m`, `--cpus=1`, `--pids-limit=256`, `--network none` by default or the `--internal` (routeless) `chaperone-crawl-internal` network with a tinyproxy allowlist proxy for the two cases that need real package-registry egress, and placeholder-only credentials (`packages/crawler/src/boot.ts`'s `PLACEHOLDER_VALUE`, never the host environment). `buildDockerArgs` was not previously exported or unit-tested; it now is, in `packages/crawler/test/boot.test.ts`. A live network-reachability test (actually booting a container and confirming it can't reach an arbitrary host) is not included — it would need Docker in every environment this suite runs in, which CI's `stack` job has but a plain `pnpm test` doesn't guarantee. What's tested is the mechanism (`--network none` yields no network device; `--network allowlist` joins the routeless internal network, never `host`/`bridge`) rather than a live proof, and that gap is stated here rather than silently assumed covered.
